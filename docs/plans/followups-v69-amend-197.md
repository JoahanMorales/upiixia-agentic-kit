- **Acceptance:**
  - each test on this list passes 20 runs in a row on the system where it failed (a loop run in CI on that system, opt-in, its result in the pull request), and the cause of each is written in the test's comment with the run that showed it; a cause that cannot be found is said plainly with what was tried, as UAK-190 did. Why: on 2026-11-24 and 25 almost every task lost one or two CI rounds of 30 to 60 minutes to a failure it did not cause. The list, with a run of each: `test_deploy_python_stdlib deploy_recognises_stdlib_python` on macOS ("Address already in use" on the port the test picked, run 45645537660); `test_setup_branches install_refuses_a_non_base_branch` timing out twice on Windows (main at aaa61b01); `test_hook_claims fresh_reads_a_crlf_epoch` on Linux (pull request #71); `test_dashboard_journey` passing only on its second run on Windows (run 45635485890); in `test_hook_session_start_speed`: `stale_lock_reclaim_runs_once` (the gate's smoke of UAK-191, "ran pace 1 and map build 0 times"), and the Windows step that died with exit code 3840 and no FAIL line while the file ran (run 45645537660, job 139315504846)
  - `test_hook_session_start_speed` is split so that no file of the kit takes more than 300 s on Windows: today it is 536 s there, so a failure of it is never retried in its job and costs a manual re-run of main. The cases about locks and simultaneous starts move to `test_hook_session_start_locks.py` and the cases about the black box flush and its clone to `test_hook_session_start_clones.py`, unchanged (moved, not rewritten: the same assertions, the lint's "tests only grow" counts a moved case as kept), and the three files carry measured timings whose Windows entry by the rule is at most 300 s. Why three: two files measured 270 s and 203 s on Windows in run 45683968328 (213 and 208 in run 45680922421), the pair adds up to 421 to 473 s per run, so even an even split passes 240 s on a slow runner and its entry passes 300
  - a test that needs a free port takes it without a race: it binds port 0 and passes the socket or the port it was given, or retries on "address in use" with another port; a helper does it once and the cases that pick a port by hand use it
  - a test's fixed sleep that waits for a process, a file or a lock is replaced by a wait on that condition with a bound, in the files of this task
  - a timing entry has room for a slow runner: an entry is the maximum measured over the runs read, per system it stands for, times 1.25, rounded up, and never less than the maximum plus 2 s; `scripts/ci_timings.py` reads the last N green runs of main with `gh`, prints for every test file the measured maximum per system and the entry the rule gives, and with `--write` rewrites the timing files it is told to, each with its `# measured DATE RUN` line. Why: with "maximum plus 1 s" a test that takes 25 to 96 s on macOS from run to run (UAK-192) forced five pushes of nothing but a number; public issue #85 lists nine files below their measurement
  - the Windows matrix has a twelfth shard when the longest shard passes 80 % of its bound: with today's table 11 shards put the longest at 1445 of 1800 s (80.3 %) and 12 put it at about 1326 s; the whole matrix is then 21 jobs, inside the cap of 22. The lint says which shard is the longest and its share
  - `test_ci_flaky.py` keeps the list of known intermittent cases in one place with, for each, the run that showed it and the task or issue that owns it; a case fixed here leaves the list, and the list is what the kit's documents and the briefs of agents cite
  - not in this task, listed in the pull request for their owners because the files belong to live tasks: `test_setup_language git_failures_are_plain` (Windows timeout), the dashboard server cases `live_url_link_is_shown_when_set` and `blocked_tasks_are_not_available` (Windows timeouts), `killed_bb_flush_is_recovered_and_published_once` (public issue #83)
